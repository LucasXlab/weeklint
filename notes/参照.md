# 参照仓库读后笔记（参照：Bowen1314/inkdove）

克隆位置：`reference/inkdove`（已加入 `.gitignore`，只读，不提交）。
阅读顺序：README.md → SPEC.md → SPEC-phase2.md「测试要求」→ DESIGN.md 第 0–2 节 → docs/deviations.md 前 20 条 → docs/external-apis.md 前 30 行 → docs/development.md → server/test/{distill,auth,sources}.test.js → `git log --format='%s'` 前 60 条。

只学做法，不学业务，不抄代码。以下每条注明出处，每个阶段开工前重读。

## 一、规格与契约

1. **把 SPEC 写成唯一契约，字段名、路由、枚举值要求一字不差。** 并行开发时任何歧义都按「最简单、能跑通」处理，并显式记录，而不是口头约定。出处：`SPEC.md` 开头「本文件是唯一契约」；`docs/development.md` 项目结构一节。
2. **错误响应统一成 `{error, code}`，HTTP 状态码与机器码分开。** 人类可读信息用中文写清楚「哪里错、对方返回什么、下一步做什么」，机器码给程序判断；规格没定的错误码集中补记。出处：`SPEC.md` 第 2 节「通用约定」；`docs/deviations.md` 第 6 条。
3. **所有外部依赖都写具体数字，不写「适当」「合理」。** 超时、重试次数、退避、并发、大小上限、限流阈值、轮询间隔都在 SPEC 里落成数字，测试直接按这些数字断言。出处：`SPEC.md` 第 4 节 LLM 客户端、4.3 防滥用；`docs/deviations.md` 第 5 条。
4. **规格里先写非目标。** 明确「不做什么」比堆功能更能防止第一版失焦；README 的「不适用于」与 SPEC 的非目标互相呼应。出处：`README.md`「适用场景 / 不适用于」；`SPEC.md` 第 0、4.3 节。
5. **开发中偏离规格必须编号记录，写清偏离了什么、为什么、影响范围。** 包括「规格没定所以补的」和「测试无法覆盖所以没做的」。出处：`docs/deviations.md` 全文（尤其第 1、3、6、20 条）。
6. **外部接口先核实再写代码，记录日期、版本、请求地址、鉴权、字段和错误格式；没核实的明确标注「未实测」。** 这条能避免把猜测写成契约。出处：`docs/external-apis.md` 全文；`SPEC.md` 第 4 节末尾「实现前先核实」。

## 二、配置、数据与安全

7. **环境变量只读项目前缀，必填项缺失或非法时拒绝启动并说明原因；通用名（如 `OPENAI_API_KEY`）一律不读。** 首次启动建管理员，之后改环境变量不覆盖数据库里的账号。出处：`SPEC.md` 第 1 节；`server/test/auth.test.js`「配置」describe。
8. **密钥只写不读：接口只回传 `xxxSet` / 末四位，日志和错误信息里不出现明文。** 写密钥的字段单独列出替换/清空规则。出处：`SPEC.md` 第 3.2 节；`server/test/auth.test.js` 对 cookie/hash 的断言。
9. **凡是从用户输入取 URL 再请求，都做 SSRF 防护：只允许 http/https，逐跳解析并拒绝内网、回环、链路本地地址，重定向也重新校验。** 出处：`SPEC.md` 第 3.3 节；`server/test/sources.test.js`「网址资料：拒绝回环、内网……」。
10. **权限判断先于存在性判断，避免通过 404/403 差异探测别人的资源。** 出处：`docs/deviations.md` 第 6 条末尾。
11. **写操作要考虑进程重启、并发冲突和部分失败；任务状态落库，重启后能继续或明确失败。** 出处：`SPEC-phase2.md` F11 测试要求「进程重启后 running 的任务接着发」；`SPEC.md` 第 3.4 节任务状态机。

## 三、测试

12. **全部测试在临时目录、mock 外部服务和注入时钟下跑，不联网、不花钱、不依赖固定等待。** 外部服务用本地假实现，等待时间注入成 0 或几百毫秒。出处：`docs/development.md`「本地开发和测试」；`server/test/helpers.js` 的 `startApp` 用法。
13. **等条件成立，不 `sleep` 固定时长。** 用轮询辅助函数等任务进入 `done/failed/cancelled`，超时才失败，失败信息写清在等什么。出处：`server/test/distill.test.js` 的 `waitJob` / `waitFor`。
14. **测试按功能分组，先测正常路径，再逐条测失败路径：参数非法、404、409、超时、限额、重复操作、重启。** 每个断言尽量落到具体字段、枚举值、数量和顺序，不只断言 200。出处：`server/test/distill.test.js` 全文；`server/test/sources.test.js` 全文；`SPEC-phase2.md`「测试要求（后端）」。
15. **纯函数单独导出并直接测。** 切块、HTML 转文本、IP 分类这类逻辑不经过 HTTP，测试更稳也更快。出处：`server/test/distill.test.js` 的 `chunkText`；`server/test/sources.test.js` 的 `htmlToText`、`isBlockedIp`。
16. **测试里检查「不该出现的东西」：密钥、密码哈希、日志字段、被忽略的脚本、重复引用。** 例如列表接口不含 log、预览不含 `<script>`、合并后引用不重复。出处：`server/test/distill.test.js` 列表断言；`server/test/sources.test.js` HTML 断言。

## 四、提交、发布与文档

17. **一个功能一个提交，提交说明写用户看得到的行为变化和关键数字，用中文，不用 `feat:` 之类空话。** 修 bug 的提交写清触发条件和影响。出处：`git log --format='%s'` 前 60 条（如「看板加『平均回复时间』……」）。
18. **发版前先跑构建检查；推 `vX.Y.Z` 标签时先校验标签与版本号一致，再跑测试、构建、建 Release；预发布不打 `latest`。** 出处：`docs/development.md`「发新版」；`.github/workflows/release.yml`。
19. **README 首屏一句话说清「给谁、做什么、靠什么做到」，紧接着是真实截图、风险须知、适用/不适用、快速开始、文档索引、许可证。** 截图必须来自真实运行，示例数据要像真的。出处：`README.md` 首屏、「使用前须知」「适用场景」「截图」「快速开始」。
20. **界面规范先写「要去掉的东西」，再写 token 和组件规则；页面 CSS 只引用 token，不写死颜色和字号。** 这套顺序能先去掉 AI 味，再谈美化。出处：`DESIGN.md` 第 0–2 节。
21. **术语统一单独做一次收尾提交：界面、报错、日志、文档里同一个概念只用一个词。** 出处：`git log` 中「统一几处术语……」「服务端提示文字改为简洁的书面用语……」「网页界面文字改为简洁的书面用语……」三条。
22. **文档分层：README 给第一次用的人，`docs/features.md` 给要深入的人，`docs/development.md` 给贡献者，`deviations.md` 给维护者，`external-apis.md` 给排障的人。** 每层只回答该层的问题。出处：`README.md` 末尾「文档」；`docs/development.md`。

## 五、会直接照搬的工程习惯

- [x] SPEC 先行，字段/路由/枚举逐字对齐，歧义记 deviations。
- [x] `{error, code}` + 中文可读信息 + HTTP 状态码（CLI 对应退出码 + `code`）。
- [x] 所有限制写成数字。
- [x] 项目前缀环境变量；非法配置拒绝启动；密钥不回传。
- [x] 外部接口先核实，记录日期和版本；不确定的标「未实测」。
- [x] 测试全部本地化：临时目录、假服务、注入时钟、等条件。
- [x] 纯函数直接测；失败路径逐条测。
- [x] 一个功能一个提交，提交说明写行为变化和数字。
- [x] 偏离规格编号记录。
- [x] README 首屏一句话 + 真实截图 + 风险 + 适用/不适用。
- [x] 设计先列「去掉什么」，再列 token；页面不写死颜色字号。
- [x] 发版校验标签与版本号一致，CI 先测试再构建。
- [x] 术语统一作为独立收尾工作。
- [x] 文档分层，不把所有东西塞进 README。

## 六、明确不照搬的部分

- 不照搬 WhatsApp / 知识库 / 多租户业务，也不引入其代码。
- 不照搬「必须 Docker + 三个容器」的部署复杂度；本项目优先一条命令即可运行。
- 不为了对齐参照仓库而引入 LLM；核心流程不需要模型，避免编造与密钥风险。
