# 许可证选择：MIT

选 MIT，不选 AGPL-3.0。

## 理由

1. **项目形态是本地 CLI + 单文件 HTML 报告**，没有服务端、没有多租户、没有网络接口。AGPL 的核心场景（用户通过网络与修改后的服务交互时须获得源码）在这里几乎不会触发，选 AGPL 只会增加采用摩擦。
2. **目标用户是个人**：学生、独立开发者、想每周花 10 秒判断「这周能不能接活」的人。他们更可能把 Weeklint 放进自己的脚本、dotfiles、Obsidian/Emacs 工作流。MIT 允许这样做，不需要公布自己的私有配置或周边脚本。
3. **没有商业授权收入计划**。项目要的是被使用和反馈，不是用 copyleft 强制商业化。
4. **依赖的许可证兼容**：`icalendar`（BSD-2-Clause）、`python-dateutil`（Apache-2.0/BSD-3-Clause 双许可）、`PyYAML`（MIT）、`rich`（MIT）、`pytest`（MIT）。MIT 项目可以依赖它们；没有 GPL 代码被复制。
5. **代码是独立编写的**：只参考了 `reference/inkdove` 的工程实践（规格驱动、偏差记录、测试约定、README 结构），没有复制其业务代码；MIT 不会与参考项目的许可证冲突。

## 不选 AGPL 的原因

- 没有网络服务，AGPL 的额外条款基本用不上；
- 个人用户和小团队会对 AGPL 的合规成本犹豫；
- 如果未来要做托管服务，再单独讨论许可证或双许可，不在 v0.1.0 提前假设。

## 边界

- 许可证不改变隐私承诺：没有网络、没有遥测、没有账号。
- 第三方依赖的许可证随依赖分发；`pip` 安装时会带上各自的 LICENSE。
- 发布到 GitHub 时，仓库根目录的 `LICENSE` 即为生效文本；不在 README 里写与 `LICENSE` 冲突的条款。
