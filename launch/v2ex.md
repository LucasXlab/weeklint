# V2EX 草稿（发布前检查节点与格式）

**标题：** 做了一个本地周计划可行性检查工具 Weeklint，想请 V 友试用

**正文：**

大家好，我是一个学生。之前每周的固定循环是：周日把任务排进日历，周四发现根本做不完，然后熬夜补。问题不在待办清单，而在「这周到底有多少分钟可用」从来没被认真算过。

Weeklint（周检）是我写的一个本地 CLI：

- 读一份 Markdown 任务（一行一个 `- [ ]`，支持 `@due`、`@estimate`、`@priority`、`@tag`、`@id`）；
- 读导出的 `.ics` 日历（支持重复事件、EXDATE、全天事件、时区和 DST）；
- `check` 先算：工作时间 − 会议 − buffer = 真正可用分钟；再和任务估算比，给出缺口和截止风险；不写文件。
- `plan` 只排能完整放下的任务，30–120 分钟一块，高优先级优先上午；放不下就整条进未排程，不会在日历上留半截任务。
- 上次确认的计划可以锁定；重跑不会把已经接受的安排打乱。
- `today` 看今天，`explain` 解释某个任务为什么排在这里/为什么没排。
- 输出 `plan.json`、`plan.ics`、`plan.md` 和一个单文件 `report.html`（浅色/深色、375px、打印）。

没有账号、没有 OAuth、没有大模型、没有联网、没有遥测。测试里会把 `socket.socket` 换成抛异常的函数，确保没有网络请求。不需要 API key。

目前明确不做/没做好的：

- 不是 CalDAV 客户端，只读导出的 `.ics`，不写回日历；
- `RECURRENCE-ID` 单次改期不合并，会跳过并 warning；
- 一次一个任务文件、最多 20 个日历；
- 没有 Windows 实机验证，CI 有 windows-latest；
- 排程是确定性规则，不是最优化。两个任务抢同一个上午时，按截止、优先级、估算、id 排序，结果可解释但不是「最优」。

想请教三个问题：

1. 容量分母：你们会按「工作时间 − 会议 − buffer」算，还是只按「深度工作时段」算？哪个更接近真实？
2. 整条回滚：放不下就整条不排，你们能接受吗？还是宁愿把最后一块拆到第二天？
3. 高优先级优先上午：这个默认对你们有帮助，还是和实际精力曲线冲突？

项目目前只在本地，未发布；先把 README、示例和截图放出来，想听真实使用场景的反馈，尤其是「算出来的缺口和你体感不一致」的情况。
